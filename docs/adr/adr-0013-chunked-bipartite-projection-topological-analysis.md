# ADR-0013: Chunked Bipartite Projection for Topological Analysis

## Status
Accepted

## Context
Projecting a bipartite package-maintainer matrix $B$ into a package-package maintainer sharing network $P = B \cdot B^T$ is computationally expensive. 
In the npm registry, the distribution of packages per maintainer follows a power-law distribution. A few maintainers (like bots or corporate accounts) maintain tens of thousands of packages.

When performing $B \cdot B^T$:
1. A maintainer with degree $D$ (maintaining $D$ packages) generates $D \times D$ edges in the projected matrix.
2. If $D = 20,000$ (common for automated publish bots), a single column in $B$ generates $400,000,000$ edges in $P$.
3. At full registry scale (millions of packages), a direct matrix multiplication $B \cdot B^T$ will result in memory exhaustion (OOM) and crash the runtime.

## Decision
We decided to:
1. Perform direct matrix multiplication for our current dataset scale (~8,000 packages), as it fits comfortably within ordinary system memory limits and takes under 0.1 seconds.
2. Establish and document a **Chunked Bipartite Projection** strategy for future scaling to full npm registry datasets:
   - Slice the matrix $B$ row-wise into smaller chunks ($B_1, B_2, \dots$).
   - Multiply chunks sequentially: $P_i = B_i \cdot B^T$.
   - Filter out weak edges (e.g., edges generated by known automated publish bots or accounts with degree $> 200$) before accumulating the results.
   - Assemble the sparse blocks into the final matrix $P$.
3. Pre-emptively filter out known automated publication accounts (e.g., regex matching `-bot`, `-ci`, or common company publish accounts) during index creation to prevent degree explosions.

## Consequences

### Positive
* **Scalability Path:** Outlines a clear, step-by-step roadmap for extending our code to the entire npm registry scale without rewriting the core mathematics.
* **Proactive Defenses:** By filtering out bots and high-degree publishing hubs, we remove noise from our maintainer graph, making the simulation focus on human developer accounts (who are the actual targets of credential theft).

### Negative
* **Algorithm Complexity:** Chunked multiplication requires coordinate tracking and block assembly, which adds complexity to the data pipeline.
